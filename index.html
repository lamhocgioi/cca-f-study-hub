1. Agentic Loop là gì?

Một agentic loop cho phép Claude tự động thực thi các tác vụ phức tạp bằng cách lặp lại một chu trình:

  1. Gửi yêu cầu tới Claude (kèm định nghĩa tool và lịch sử hội thoại)
  2. Claude quyết định gọi tool nào (do model điều khiển, không phải cấu hình sẵn)
  3. Thực thi tool
  4. Trả kết quả về cho Claude
  5. Lặp lại cho đến khi tác vụ hoàn tất

Điểm mấu chốt: Claude quyết định gọi tool nào dựa trên context. Đây không phải là cây quyết định được cấu hình sẵn — mà là model tự suy luận về hành động tiếp theo.

2. stop_reason: Tín hiệu Điều khiển Cốt lõi

Mỗi phản hồi từ Claude API đều bao gồm một stop_reason. Đây là cơ chế chính để điều khiển luồng loop:

stop_reason: "tool_use"
  → Claude wants to execute a tool
  → YOU must: execute the tool(s), append results, call the API again

stop_reason: "end_turn"
  → Claude has completed the task
  → YOU must: return the response to the user

Vì sao stop_reason quan trọng

Dùng bất cứ thứ gì khác ngoài stop_reason làm cơ chế điều khiển loop chính là một anti-pattern:

  • Phân tích văn bản ("if 'done' in response") → không đáng tin cậy; cách diễn đạt của model thay đổi
  • Dùng giới hạn số vòng lặp tùy ý làm cơ chế chính → cắt ngang các tác vụ chưa hoàn tất
  • stop_reason → mang tính tất định, luôn hiện diện, được thiết kế đúng cho mục đích này

3. Vòng đời của Agentic Loop

USER REQUEST
     │
     ▼
Send request to Claude API
(includes: tools, conversation history)
     │
     ▼
Receive response
     │
     ▼
Check stop_reason
     ├── "tool_use" → Execute tool(s)
     │                  ↓
     │              Append tool results to history
     │                  ↓
     │              Call API again (loop continues)
     │
     └── "end_turn" → Return response to user (loop ends)

4. Tool Results và Lịch sử Hội thoại

Khi Claude yêu cầu một tool, bạn phải thêm hai mục vào lịch sử hội thoại:

  ]
}

  "content": [
    {
      "type": "tool_result",

      "content": "{\"name\": \"Jane Smith\", \"status\": \"verified\", \"tier\": \"premium\"}"

Cực kỳ quan trọng: Cả hai mục phải được thêm vào trước lần gọi API tiếp theo. Model cần thấy cả yêu cầu tool call của chính nó VÀ kết quả mà nó tạo ra.

5. Anti-Patterns

❌ Anti-Pattern 1: Phân tích Văn bản để Phát hiện Hoàn tất

# WRONG — text-based completion detection
def bad_loop(messages):
    for i in range(10):
        response = client.messages.create(...)
        text = response.content[0].text if response.content else ""
        if "final answer" in text.lower() or "done" in text.lower():
            return text  # Unreliable — wording varies
    return "Timed out"

❌ Anti-Pattern 2: Dùng Giới hạn Số vòng lặp làm Cơ chế Điều khiển Chính

# WRONG — arbitrary cap interrupts incomplete tasks
def bad_loop(messages):
    for _ in range(5):  # Cap is the PRIMARY termination check
        response = client.messages.create(...)
        if response.stop_reason == "end_turn":
            return extract_text(response)
        # ... execute tools ...
    return "Max iterations reached"  # Task may be unfinished!

✅ Đúng: stop_reason là Cơ chế Chính, Giới hạn Số vòng lặp là Lưới An toàn

def good_loop(messages):
    MAX_SAFETY = 50  # Safety net for infinite loop bugs only
    for _ in range(MAX_SAFETY):
        response = client.messages.create(...)
        
        if response.stop_reason == "end_turn":  # PRIMARY control
            return extract_text(response)
        elif response.stop_reason == "tool_use":
            messages = append_and_execute(messages, response)
        else:
            raise ValueError(f"Unexpected stop_reason: {response.stop_reason}")
    
    raise RuntimeError("Safety limit reached — possible infinite loop bug")

def run_agentic_loop(user_message: str) -> str:
    """
    Correct agentic loop implementation:
    - stop_reason controls loop flow (primary)
    - Tool results appended to conversation history
    - Iteration cap as safety net only
    """
    messages = [{"role": "user", "content": user_message}]

    system_prompt = (
        "You are a customer support agent. "
        "Always verify customer identity before any order operation. "
        "Required workflow: get_customer → lookup_order → process_refund (if needed)."
    )

    MAX_SAFETY = 50
    for iteration in range(MAX_SAFETY):
        response = client.messages.create(
            model="claude-opus-4-5",
            max_tokens=4096,
            system=system_prompt,
            tools=tools,
            messages=messages
        )

        # PRIMARY control: stop_reason
        if response.stop_reason == "end_turn":
            for block in response.content:
                if hasattr(block, 'text'):
                    return block.text
            return "Task completed."

        elif response.stop_reason == "tool_use":
            # Step 1: Append Claude's response (tool call) to history
            messages.append({
                "role": "assistant",
                "content": response.content
            })

            # Step 2: Execute each requested tool
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"  Executing: {block.name}({block.input})")
                    result = execute_tool(block.name, block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result
                    })

            # Step 3: Append tool results to history
            messages.append({
                "role": "user",
                "content": tool_results
            })
            # Loop continues...

        else:
            raise ValueError(f"Unexpected stop_reason: {response.stop_reason}")

    raise RuntimeError("Safety iteration limit reached — check for infinite loop bug")

Bài tập A: Sửa Loop bị Lỗi

Xác định và sửa tất cả lỗi trong đoạn triển khai này:

def buggy_loop(user_msg):
    messages = [{"role": "user", "content": user_msg}]
    
    for i in range(3):  # BUG 1
        response = client.messages.create(
            model="claude-opus-4-5",
            max_tokens=1000,
            tools=tools,
            messages=messages
        )
        
        text = ""
        for block in response.content:
            if hasattr(block, 'text'):
                text = block.text
                break
        
        if "final answer" in text:  # BUG 2
            return text
        
        if response.stop_reason == "tool_use":
            for block in response.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)
                    messages.append({   # BUG 3: missing assistant append
                        "role": "user",
                        "content": result  # BUG 4: wrong format
                    })
    
    return text

Các lỗi cần tìm:

  1. Dùng giới hạn số vòng lặp làm cơ chế chính (đáng lẽ phải là lưới an toàn)
  2. Phân tích văn bản để phát hiện hoàn tất (nên dùng stop_reason)
  3. Thiếu bước thêm message của assistant trước tool results
  4. Định dạng nội dung tool result sai (phải là list với type tool_result)

1. Kiến trúc Hub-and-Spoke

Trong các hệ thống multi-agent, coordinator là trung tâm (hub) quản lý toàn bộ subagent:

                    ┌─────────────────┐
                    │   COORDINATOR   │
                    │                 │
                    │ • Decomposition │
                    │ • Delegation    │
                    │ • Aggregation   │
                    │ • Error handling│
                    └────────┬────────┘
                             │ (Hub)
         ┌───────────────────┼───────────────────┐
         │                   │                   │
         ▼                   ▼                   ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  Web Search  │    │   Document   │    │  Synthesis   │
│   Subagent   │    │   Analysis   │    │   Subagent   │
│              │    │   Subagent   │    │              │
│ Isolated ctx │    │ Isolated ctx │    │ Isolated ctx │
└──────────────┘    └──────────────┘    └──────────────┘

Quy tắc cốt lõi: Các subagent KHÔNG giao tiếp trực tiếp với nhau. Mọi giao tiếp giữa các agent đều đi qua coordinator.

2. Trách nhiệm của Coordinator

Coordinator nắm giữ năm chức năng then chốt:

  1. Analyze (phân tích) các yêu cầu của truy vấn (chủ đề, phạm vi, subagent cần dùng)
  2. Decompose (phân rã) thành các subtask riêng biệt, không chồng lấn
  3. Delegate (ủy thác) kèm context tường minh cho từng subagent
  4. Aggregate (tổng hợp) kết quả từ tất cả subagent
  5. Evaluate (đánh giá) độ bao phủ và ủy thác lại nếu phát hiện lỗ hổng (tinh chỉnh lặp)

3. Context Isolation: Quy tắc Quan trọng Nhất

Subagent KHÔNG tự động kế thừa context từ coordinator.

# ❌ WRONG — assumes context inheritance
coordinator_system = "Research topic: AI in creative industries"

subagent_prompt = "Search for relevant articles"
# → Subagent has NO IDEA what topic to search!

# ✅ CORRECT — explicit context in every subagent prompt
subagent_prompt = """
Research topic: Impact of AI on creative industries
YOUR SPECIFIC FOCUS: Music industry (AI composition tools, royalties, production)
Time frame: 2022-2025

Search for articles covering:
- Musicians and composers using AI tools
- AI-generated music platforms
- Copyright and royalty implications

Return findings as a structured list with source URLs and dates.
"""

Mỗi subagent nhận toàn bộ context cần thiết ngay trong prompt của chính nó. Không chia sẻ context giữa các subagent, và không kế thừa từ session của coordinator.

4. Lựa chọn Động so với Chạy Toàn bộ Pipeline

❌ Inefficient: Always invoke the full pipeline
Query: "What is prompt chaining?"
→ Invoke web search agent (unnecessary for factual Q)
→ Invoke document analysis agent (unnecessary)
→ Invoke synthesis agent
→ Invoke report generator
(Slow, expensive, overkill)

✅ Efficient: Dynamic selection based on query needs
Query: "What is prompt chaining?"
→ Coordinator analyzes: Simple factual question
→ Invoke ONLY synthesis agent with existing knowledge
→ Return answer (fast, cheap)

Query: "Analyze 5 recent papers on AI safety"
→ Coordinator analyzes: Needs research + analysis + synthesis
→ Invoke web search + document analysis + synthesis agents

5. Rủi ro: Phân rã Tác vụ Quá Hẹp

Từ Exam Scenario 3, Q7: Coordinator phân rã "AI in creative industries" chỉ thành các subtopic về nghệ thuật thị giác (visual arts), bỏ sót âm nhạc, văn học và điện ảnh.

❌ Narrow decomposition (only covers visual arts):
1. "AI in digital painting"
2. "AI in graphic design"
3. "AI in photography"
→ Missing: music, writing, film, performance!

✅ Broad decomposition (covers all creative sectors):
1. "AI in visual arts (painting, digital art, graphic design, photography)"
2. "AI in music (composition, production, AI-generated music, royalties)"
3. "AI in literary content (journalism, fiction, screenwriting)"
4. "AI in film and video production (VFX, editing, distribution)"

Bước decomposition của coordinator có tính quyết định — lỗ hổng ở đây sẽ lan truyền qua toàn bộ pipeline.

2. Spawn Subagent Song song

Song song (Parallel): Coordinator phát ra nhiều Task call trong một phản hồi duy nhất — tất cả thực thi đồng thời:

Tuần tự (Sequential): Coordinator phát ra các Task call ở các lượt riêng biệt — chạy lần lượt (chậm hơn):

Turn 1: Task(area: music) → wait for result

Dùng parallel spawning khi các subagent độc lập với nhau (không có phụ thuộc dữ liệu giữa chúng).

2. PostToolUse Hook: Chuẩn hóa Dữ liệu

Khi nhiều MCP tool trả về các định dạng khác nhau (Unix timestamp, mã trạng thái dạng số, cấu trúc khác nhau), PostToolUse chuẩn hóa mọi thứ trước khi Claude nhìn thấy:

import json
from datetime import datetime

STATUS_MAP = {0: "pending", 1: "processing", 2: "shipped",
              3: "delivered", 4: "cancelled", 5: "refunded"}

def post_tool_use_normalizer(tool_name: str, raw_result: str) -> str:
    """
    Normalize heterogeneous data formats from different MCP tools.
    Claude receives consistent, normalized data.
    """
    try:
        result = json.loads(raw_result)
    except json.JSONDecodeError:
        return raw_result  # Pass through if not JSON

    # Normalize Unix timestamps → ISO 8601
    for field in ["created_at", "updated_at", "shipped_at"]:
        if field in result and isinstance(result[field], int):
            result[field] = datetime.fromtimestamp(result[field]).isoformat()

    # Normalize date strings (YYYYMMDD → YYYY-MM-DD)
    for field in ["order_date", "delivery_date"]:
        if field in result and isinstance(result[field], str) and len(result[field]) == 8:
            d = result[field]
            result[field] = f"{d[:4]}-{d[4:6]}-{d[6:8]}"

    # Normalize numeric status codes → readable strings
    if "status_code" in result and isinstance(result["status_code"], int):
        result["status"] = STATUS_MAP.get(result["status_code"], "unknown")
        result["status_code_raw"] = result.pop("status_code")  # Preserve for debug

    # Normalize currency (cents → dollars for US tools)
    if "amount_cents" in result:
        result["amount"] = result.pop("amount_cents") / 100
        result["currency"] = "USD"

    return json.dumps(result)

import json
from pathlib import Path

class SessionManager:
    """Manages session state for resumable agentic workflows."""

    def __init__(self, session_name: str):
        self.session_name = session_name
        self.state_file = Path(f".claude_sessions/{session_name}.json")
        self.state_file.parent.mkdir(exist_ok=True)

    def save_state(self, state: dict) -> None:
        """Persist state after each completed unit (crash-safe)."""
        import datetime
        state["session_name"] = self.session_name
        state["saved_at"] = datetime.datetime.now().isoformat()
        self.state_file.write_text(json.dumps(state, indent=2))
        print(f"State saved: {self.session_name}")

    def load_state(self) -> dict | None:
        """Load state at session start to check for resumption."""
        if self.state_file.exists():
            return json.loads(self.state_file.read_text())
        return None

    def create_resume_context(self, state: dict) -> str:
        """
        Create structured summary to inject into a new session.
        Use when tool results are stale (files changed) — better than raw --resume.
        """
        return f"""
RESUMING TASK: {state['session_name']}

COMPLETED WORK (do not redo these):
{json.dumps(state.get('completed_tasks', []), indent=2)}

CURRENT STATE:
- Files analyzed: {state.get('files_analyzed', [])}
- Key findings: {state.get('key_findings', [])}
- Next pending task: {state.get('next_task', 'None')}

FILE CHANGES SINCE LAST SESSION:
{state.get('file_changes', 'None reported')}

INSTRUCTION: Focus on "{state.get('next_task', 'continuing the analysis')}".
Do NOT re-analyze already-completed work.
"""

    def fork(self, fork_name: str, approach: str) -> "SessionManager":
        """Fork session to explore a different approach from the same baseline."""
        base_state = self.load_state() or {}
        fork_mgr = SessionManager(f"{self.session_name}-{fork_name}")
        fork_state = {
            **base_state,
            "forked_from": self.session_name,
            "approach": approach
        }
        fork_mgr.save_state(fork_state)
        print(f"Forked: {fork_mgr.session_name} (Approach: {approach})")
        return fork_mgr

1. Vì sao Tool Description quan trọng

LLM dùng tool description làm tín hiệu chính để quyết định gọi tool nào. Model KHÔNG đọc code, database schema hay backend logic của bạn — nó chỉ nhìn thấy phần description mà bạn cung cấp.

Insight quan trọng: Khi hai tool có description tối thiểu hoặc chồng lấn nhau, model coi chúng có thể thay thế cho nhau. Điều này dẫn tới misrouting — gọi get_customer trong khi lẽ ra cần lookup_order.

Pipeline lựa chọn (The Selection Pipeline)

User input → Model reasoning → Tool description matching → Tool call

Model so sánh ý nghĩa ngữ nghĩa (semantic) của yêu cầu người dùng với description của từng tool. Description mơ hồ làm sụp đổ quá trình matching này.

Hệ quả thực tế (từ Exam Scenario 1)

Production logs cho thấy agent thường xuyên gọi get_customer khi người dùng hỏi về đơn hàng (ví dụ: "check my order #12345"), thay vì gọi lookup_order. Cả hai tool đều có description tối thiểu ("Retrieves customer information" / "Retrieves order details").

Root cause: Description tối thiểu. Cách khắc phục là mở rộng description, không phải thêm few-shot examples hay thêm routing layer.

3. Anti-Patterns: Description tệ trông như thế nào

❌ Anti-Pattern 1: Minimal Description

tools = [
    {
        "name": "get_customer",
        "description": "Retrieves customer information",  # TOO VAGUE
        "input_schema": { ... }
    },
    {
        "name": "lookup_order",
        "description": "Retrieves order details",  # TOO VAGUE
        "input_schema": { ... }
    }
]

Problem: Cả hai description đều dùng từ "retrieves" + một danh từ mơ hồ. Model không có cơ sở nào để phân biệt chúng.

❌ Anti-Pattern 2: Overlapping Names

# analyze_content vs analyze_document — near-identical names and descriptions
# Model will misroute between them

❌ Anti-Pattern 3: Generic Verbs Without Context

"description": "Processes the request and returns data"
# This description fits any tool in any system — useless for selection

4. Tách (Splitting) hay Gộp (Consolidating) tool

Khi nào nên tách (Split)

Tách một generic tool thành các tool chuyên biệt theo mục đích khi:

  • Một tool đơn lẻ xử lý 3+ workflow khác biệt
  • Các caller khác nhau cần các tập con chức năng khác nhau
  • Tool description buộc phải nói "depending on the input, this tool does X or Y"

Example: Tách analyze_document thành:

  • extract_data_points — cho trích xuất số liệu/dữ liệu có cấu trúc
  • summarize_content — cho tóm tắt văn xuôi
  • verify_claim_against_source — cho kiểm chứng thông tin (fact-checking)

Khi nào nên gộp (Consolidate)

Gộp khi:

  • Hai tool luôn được gọi cùng nhau (gộp thành một với schema hợp nhất)
  • Sự khác biệt giữa các tool là vô hình đối với LLM (chi tiết triển khai, không phải khác biệt về ngữ nghĩa)

Ma trận quyết định (Decision Matrix)

Is the distinction semantically clear to the LLM?
  YES → Keep separate, improve descriptions
  NO  → Consolidate OR rename to make distinction clear

1. MCP isError Pattern

MCP tools báo hiệu thất bại cho agent bằng cách dùng flag isError trong tool result. Điều này khác biệt căn bản với việc throw một exception — agent nhận error dưới dạng dữ liệu mà nó có thể suy luận (reason) về.

Vì sao Structured Errors quan trọng

Generic error → "Operation failed"
  → Agent cannot determine: is this retryable? what was attempted? what alternatives exist?
  → Agent makes a random recovery decision (or gives up)

Structured error → {isError: true, errorCategory: "transient", isRetryable: true, ...}
  → Agent knows: retry this specific subagent with same query
  → Agent makes an informed recovery decision

Schema của isError Response

# Minimal compliant error response
{
    "isError": True,
    "errorCategory": "transient",   # transient | validation | business | permission
    "isRetryable": True,
    "errorCode": "DB_TIMEOUT",
    "message": "Database connection timed out after 30s",
    "hint": "Retry after 5 seconds; backend is under load"
}

2. Error Taxonomy: Bốn category

Category 1: Transient Errors

Definition: Thất bại tạm thời do hạ tầng (infrastructure) gây ra, không phải do bản thân request. Examples: Timeouts, service unavailability, rate limiting, network errors isRetryable: True — cùng một request nhiều khả năng sẽ thành công khi retry Agent behavior: Chờ một chút rồi retry với tham số y hệt

Category 2: Validation Errors

Definition: Input không khớp với format hoặc ràng buộc mà tool mong đợi. Examples: Invalid order ID format, missing required field, type mismatch isRetryable: False — retry với cùng input sẽ lại thất bại; cần tái tạo (reformulate) request Agent behavior: Báo cáo vấn đề validation cho người dùng hoặc tái tạo lại input

Category 3: Business Errors

Definition: Request đúng cú pháp nhưng vi phạm một business rule. Examples: Refund amount exceeds policy limit, account is suspended, return window expired isRetryable: False — business rule đang chặn, không phải vấn đề kỹ thuật Agent behavior: Giải thích ràng buộc chính sách (policy) cho người dùng; không retry

Category 4: Permission Errors

Definition: Caller không có quyền (authorization) cho thao tác được yêu cầu. Examples: Agent không có quyền truy cập financial records, scope restriction isRetryable: Tùy thuộc vào việc auth có thể được refresh hay không Agent behavior: Yêu cầu quyền truy cập cao hơn hoặc escalate cho con người

3. Retryable vs Non-Retryable Errors

Boolean isRetryable là cực kỳ quan trọng để ngăn lãng phí API calls. Không có nó, agent thường retry vô hạn các lỗi non-retryable (vi phạm business rule).

isRetryable: True  → Agent should retry (with optional backoff)
isRetryable: False → Agent should NOT retry; communicate to user or escalate

Cây quyết định Retry (The Retry Decision Tree)

Tool returns isError: True
        ↓
Check isRetryable
    ├── True  → Check errorCategory
    │           ├── transient → Retry with same params (max 3 attempts)
    │           └── validation → Retry with corrected params
    └── False → Check errorCategory
                ├── business → Communicate policy to user
                └── permission → Escalate or request auth

4. Access Failures vs Valid Empty Results

Sự phân biệt này thường xuyên được kiểm tra trong kỳ thi. Đây là hai kết cục hoàn toàn khác nhau:

TypeMeaningisErrorAgent Action
Access failureTool không thể thực thi (timeout, auth error, service down)TrueCần quyết định retry
Valid empty resultTool thực thi thành công; không tìm thấy dữ liệu khớpFalseBáo "no results found" cho người dùng

Lỗi thường gặp (Common Mistake)

# ❌ WRONG: Returning isError for "no results" masks success as failure
def lookup_order(order_id):
    result = db.query(order_id)
    if not result:
        return {"isError": True, "message": "Order not found"}  # WRONG!
    return result

# ✅ CORRECT: Empty result is a valid successful outcome
def lookup_order(order_id):
    result = db.query(order_id)
    if not result:
        return {
            "isError": False,           # Successful execution
            "found": False,             # No match — valid outcome
            "message": f"No order found with ID {order_id}",
            "searched": order_id
        }
    return {"isError": False, "found": True, "order": result}

5. Local Recovery vs Coordinator Escalation

Nguyên tắc (The Principle)

Subagent nên xử lý transient failures tại chỗ (locally) khi có thể. Chỉ propagate lên coordinator khi local recovery đã cạn kiệt hoặc khi lỗi cần quyết định ở cấp coordination.

Subagent encounters error
        ↓
Can I handle this locally?
    ├── YES (transient, retry budget available)
    │   → Retry locally, up to 3 times with backoff
    │   → If resolved: return success + partial results note
    │   → If unresolved: escalate with full context
    └── NO (business, permission, exhausted retries)
        → Propagate structured error to coordinator
        → Include: what was attempted, partial results, alternatives

Cần bao gồm những gì khi Escalating

# What the coordinator needs to make a recovery decision:
{
    "isError": True,
    "errorCategory": "transient",
    "failureType": "timeout",
    "attemptedQuery": "search for AI in creative industries 2024",
    "attemptsCount": 3,
    "partialResults": [
        # Any results obtained before the failure
        {"source": "techcrunch.com", "title": "AI Artists 2024", "relevance": 0.9}
    ],
    "alternativeApproaches": [
        "Try narrowing query to 'AI visual arts 2024'",
        "Use document analysis agent on cached sources instead"
    ],
    "isRetryable": True,
    "hint": "Service is overloaded; retry after 30 seconds"
}

    errorCode: str = ""
    message: str = ""
    hint: str = ""
    attemptedInput: Optional[dict] = None
    partialResults: Optional[list] = None
    alternativeApproaches: Optional[list] = None

    def to_dict(self):
        return {k: v for k, v in asdict(self).items() if v is not None}

def process_refund(customer_id: str, order_id: str, amount: float, reason: str) -> dict:
    """
    Refund tool with structured error responses for each failure category.
    """
    # Validation error: check input format
    if not customer_id.startswith("CUST-"):
        return MCPToolError(
            isError=True,
            errorCategory=ErrorCategory.VALIDATION,
            isRetryable=False,
            errorCode="INVALID_CUSTOMER_ID",
            message=f"Customer ID '{customer_id}' is invalid. Format: CUST-XXXXX",
            hint="Re-fetch the customer ID using get_customer first",
            attemptedInput={"customer_id": customer_id}
        ).to_dict()

    # Business error: policy violation — non-retryable
    if amount > 500:
        return MCPToolError(
            isError=True,
            errorCategory=ErrorCategory.BUSINESS,
            isRetryable=False,
            errorCode="EXCEEDS_REFUND_LIMIT",

            alternativeApproaches=[
                "Use escalate_to_human with refund_amount and reason",
                "Offer partial refund up to $500 and escalate remainder"
            ]
        ).to_dict()

    # Permission error: agent not authorized
    if not _check_refund_permission(customer_id):
        return MCPToolError(
            isError=True,
            errorCategory=ErrorCategory.PERMISSION,
            isRetryable=False,
            errorCode="INSUFFICIENT_PERMISSIONS",
            message="This agent session is not authorized to process refunds for this account tier",
            hint="Escalate to a senior agent with refund authorization"
        ).to_dict()

    # Transient error: simulate infrastructure issue
    try:
        result = _call_refund_api(customer_id, order_id, amount, reason)
        return {
            "isError": False,
            "refundId": result["id"],

# --- Subagent with Local Recovery ---

def web_search_subagent_with_recovery(query: str, max_retries: int = 3) -> dict:
    """
    Demonstrates local recovery for transient failures before escalating.
    """
    partial_results = []
    last_error = None

    for attempt in range(max_retries):
        try:
            results = _search_web(query)
            return {
                "isError": False,
                "results": results,
                "query": query,
                "retrievedAt": time.time()
            }
        except TimeoutError as e:
            last_error = str(e)
            if attempt < max_retries - 1:
                time.sleep(2 ** attempt)  # exponential backoff: 1s, 2s, 4s
            continue
        except ValueError as e:
            # Non-retryable validation error — escalate immediately
            return MCPToolError(
                isError=True,
                errorCategory=ErrorCategory.VALIDATION,
                isRetryable=False,
                errorCode="INVALID_QUERY",
                message=str(e),
                attemptedInput={"query": query}
            ).to_dict()

    # All retries exhausted — return structured error with partial context
    return MCPToolError(
        isError=True,
        errorCategory=ErrorCategory.TRANSIENT,
        isRetryable=True,  # Coordinator can try later
        errorCode="SEARCH_TIMEOUT",
        message=f"Web search timed out after {max_retries} attempts: {last_error}",
        attemptedInput={"query": query},
        partialResults=partial_results,
        alternativeApproaches=[
            f"Retry with narrower query: '{query.split()[0]} {query.split()[-1]}'",
            "Use document analysis agent on cached sources"
        ],
        hint=f"Last error: {last_error}"
    ).to_dict()

def handle_tool_error(tool_name: str, error_response: dict, messages: list) -> str:
    """
    Agent-side logic for processing structured errors.
    """
    category = error_response.get("errorCategory", "unknown")
    is_retryable = error_response.get("isRetryable", False)
    message = error_response.get("message", "Unknown error")
    hint = error_response.get("hint", "")

    if category == "transient" and is_retryable:
        # Retry with backoff
        return f"RETRY:{tool_name}"

    elif category == "business":
        # Communicate policy constraint to user
        return f"RESPOND:I cannot process this request automatically: {message}"

    elif category == "permission":
        # Escalate
        return "ESCALATE:human_agent"

    elif category == "validation":
        # Ask user to clarify or reformulate
        return f"CLARIFY:{message}. {hint}"

    else:
        return f"RESPOND:An unexpected error occurred: {message}"

1. Principle of Least Privilege cho Tools

Mỗi agent chỉ nên có quyền truy cập đúng những tool cần cho vai trò cụ thể của nó. Đây chính là nguyên tắc bảo mật least privilege được áp dụng cho việc dùng tool của LLM.

Vì sao điều này quan trọng:

  • Giảm cognitive load cho model (ít lựa chọn hơn = quyết định tốt hơn)
  • Ngăn nhầm lẫn vai trò (synthesis agent lại đi làm web search)
  • Cải thiện observability (tool call bất thường cho thấy rõ có misconfiguration)
  • Thực thi các boundary về kiến trúc

Ví dụ Ánh xạ Role → Tool (Multi-Agent Research System)

Coordinator Agent → [Task, escalate_to_human]
Web Search Agent  → [search_web, fetch_url]  
Document Agent    → [load_document, extract_text, extract_data_points]
Synthesis Agent   → [verify_fact, write_section]  ← scoped cross-role tool
Report Agent      → [format_report, write_file]

2. Quá nhiều Tool làm giảm độ tin cậy

Exam fact: Cấp cho một agent 18 tool thay vì 4-5 tool làm giảm độ tin cậy của tool selection bằng cách tăng độ phức tạp của quyết định.

Vì sao điều này xảy ra

Model phải đánh giá mọi tool description cho mỗi quyết định hành động. Với 18 tool:

  • Không gian quyết định lớn hơn 18× mỗi lượt
  • Các tool tương tự nhau xuất hiện thường xuyên hơn một cách ngẫu nhiên, gây nhầm lẫn
  • System prompt và tool description cạnh tranh nhau về không gian context window

Quy tắc 4-5 Tool (The 4-5 Tool Rule)

Mỗi agent theo mỗi role: tối đa 4-5 tool để có độ tin cậy chọn tool tối ưu.

Agents with 4-5 tools: reliable selection
Agents with 10+ tools: selection errors increase
Agents with 18+ tools: significant misrouting

Cross-Role Tool Access

Đôi khi một agent chuyên biệt cần một tool từ domain khác cho các nhu cầu tần suất cao. Hãy cấp nó trực tiếp (scoped), và route các trường hợp phức tạp qua coordinator.

Thay thế các generic tool bằng các phương án ràng buộc (constrained) để thực thi boundary:

# BEFORE: Generic fetch_url — can fetch any URL
# AFTER: load_document — validates only document URLs, rejects external sites

def load_document(url: str) -> dict:
    """
    Constrained replacement for fetch_url.
    Only accepts URLs from approved document storage domains.
    Prevents synthesis agent from making arbitrary web requests.
    """
    allowed_domains = ["docs.company.com", "storage.company.com", "drive.google.com"]
    from urllib.parse import urlparse
    domain = urlparse(url).netloc
    
    if not any(domain.endswith(d) for d in allowed_domains):
        return {
            "isError": True,
            "errorCategory": "validation",
            "isRetryable": False,
            "message": f"URL domain '{domain}' is not an approved document source",
            "hint": "For web search, use the web search agent through the coordinator"
        }
    
    # Fetch and return document content
    return _fetch_and_parse(url)

4. Cấu hình tool_choice

tool_choice kiểm soát việc model có phải gọi tool hay không và gọi tool nào. Ba mode:

Mode 1: "auto" (Default)

# Model decides: may call a tool OR return conversational text
response = client.messages.create(
    model="claude-opus-4-5",
    tools=tools,
    tool_choice={"type": "auto"},  # or omit entirely
    messages=messages
)
# Risk: model may respond with text when you need a structured tool call

Mode 2: "any"

# Model MUST call a tool — any tool from the available list
response = client.messages.create(
    model="claude-opus-4-5",
    tools=tools,
    tool_choice={"type": "any"},
    messages=messages
)
# Use when: you need guaranteed tool output, don't care which tool
# Example: forcing structured output when multiple extraction schemas exist

Mode 3: Forced (Specific Tool)

# Model MUST call exactly this named tool
response = client.messages.create(
    model="claude-opus-4-5",
    tools=tools,
    tool_choice={"type": "tool", "name": "extract_metadata"},
    messages=messages
)
# Use when: a specific tool must run first before subsequent steps
# Example: always extract_metadata before enrichment tools

Decision Framework

Do I need a tool call at all?
  NO  → "auto" or no tool_choice
  YES → Do I need a specific tool?
          NO  → "any" (guarantees tool call, model picks)
          YES → forced {"type": "tool", "name": "..."}

Ép thứ tự nhiều bước (Multi-Step Forced Sequencing)

# Use forced selection to ensure correct ordering:
# Step 1: Force extract_metadata
# Step 2: Use results in next turn with "auto"

def two_step_extraction(document: str):
    messages = [{"role": "user", "content": f"Extract from: {document}"}]
    
    # Step 1: Force metadata extraction first
    response1 = client.messages.create(
        model="claude-opus-4-5",
        tools=all_tools,
        tool_choice={"type": "tool", "name": "extract_metadata"},
        messages=messages
    )
    
    # Add tool result to conversation
    messages.append({"role": "assistant", "content": response1.content})
    metadata_result = get_tool_result(response1)
    messages.append({"role": "user", "content": [{"type": "tool_result", ...}]})
    
    # Step 2: Allow model to choose enrichment tool based on metadata
    response2 = client.messages.create(
        model="claude-opus-4-5",
        tools=all_tools,
        tool_choice={"type": "auto"},  # Now model picks appropriate enrichment
        messages=messages
    )
    
    return response2

3. MCP Resources vs MCP Tools

Hai primitive khác biệt của MCP phục vụ những mục đích khác nhau:

MCP Tools

  • What: Các hành động (actions) mà agent có thể invoke
  • Characteristics: Nhận input, tạo output, có side effects
  • Examples: search_issues, create_task, run_query, send_email
  • Usage: Khi agent cần làm gì đó

MCP Resources

  • What: Catalog nội dung hoặc dữ liệu mà agent có thể đọc
  • Characteristics: Read-only, phơi bày nội dung có cấu trúc, giảm số exploratory tool calls
  • Examples: Issue summaries, documentation hierarchies, database schemas, API catalogs
  • Usage: Khi agent cần biết có gì sẵn có trước khi quyết định làm gì

Vì sao Resources quan trọng cho Context Efficiency

Without resources:
  Agent calls search_issues("*") → gets all 200 issues → wastes context on irrelevant items
  Agent calls search_issues("bug") → gets some items → calls again → iterative exploration

With resources:
  Agent reads resource: IssuesSummary → sees: 
    "Open Issues: 47 bugs, 12 features, 8 security. Top priority: AUTH-001, PERF-023, SEC-007"
  Agent makes targeted tool call: get_issue("AUTH-001")
  Saves 5-10 exploratory tool calls

Triển khai MCP Resources trong một Server

4. Tool Discovery và Simultaneous Access

Key exam fact: Tools từ tất cả các MCP server đã cấu hình được discover tại connection time và có sẵn đồng thời (simultaneously) cho agent.

Agent không cần "chuyển đổi" (switch) giữa các MCP server. Tất cả tool xuất hiện trong một tool namespace hợp nhất duy nhất.

.mcp.json configures:
  - github MCP server: [list_prs, get_pr, create_comment]
  - jira MCP server: [list_issues, update_issue, add_comment]
  - company-db MCP server: [run_query, get_schema]

Agent sees at runtime:
  Available tools: [list_prs, get_pr, create_comment, list_issues, 
                   update_issue, add_comment, run_query, get_schema]
  + All Claude Code built-in tools (Read, Write, Grep, Glob, etc.)

Tăng cường MCP Tool Description để được ưu tiên dùng (Adoption)

Built-in tools (Grep, Glob) có description đã được hiểu rõ. Custom MCP tools cần description rõ ràng, chi tiết để cạnh tranh:

// ❌ Weak description — agent prefers Grep instead
{
  "name": "semantic_search_codebase",
  "description": "Searches the codebase"
}

// ✅ Strong description — agent understands when to choose this over Grep
{
  "name": "semantic_search_codebase",  
  "description": "Semantically searches the entire codebase using AI embeddings. Unlike Grep which matches exact text patterns, this tool understands meaning and finds conceptually related code. Use when: searching by concept ('where is authentication handled'), finding similar implementations, or when exact string is unknown. Returns: file path, line number, relevance score, code snippet. Much more effective than Grep for exploratory code understanding."
}

2. Grep vs Glob: Content vs Path

Đây là cặp hay bị nhầm lẫn nhất.

Grep → Tìm BÊN TRONG file

Use Grep when you need to find: where is this code?
- "Find all callers of function processRefund()"
- "Which files import from './auth/tokens'?"
- "Where is the error message 'Invalid token' defined?"
- "What files reference the CUSTOMER_TIER constant?"

Glob → Tìm TÊN FILE

Use Glob when you need to find: which files exist?
- "Find all test files" → **/*.test.tsx
- "Find all Terraform files" → terraform/**/*.tf  
- "Find all TypeScript interface files" → src/**/*.interface.ts
- "Find all Python files in the utils directory" → utils/**/*.py

Quy tắc quyết định (Decision Rule)

"I'm looking for text/code INSIDE files"  → Grep
"I'm looking for files that MATCH a name" → Glob

3. Read / Write / Edit: Khi nào dùng cái nào

Edit — Ưu tiên cho thay đổi có định hướng

# Edit uses unique text matching to find and replace a specific section
# Works when: old_str appears EXACTLY ONCE in the file

Edit(
    path="src/auth/tokens.ts",
    old_str="""
function validateToken(token: string): boolean {
    return tokens.includes(token);
}""",
    new_str="""
async function validateToken(token: string): Promise<boolean> {
    const cached = await cache.get(token);
    if (cached !== null) return cached;
    const valid = tokens.includes(token);
    await cache.set(token, valid, TTL_SECONDS);
    return valid;
}"""
)

Edit thất bại khi: old_str xuất hiện ở nhiều nơi (code bị trùng lặp, pattern lặp lại). Trong trường hợp này, Edit sẽ throw một error về non-unique match.

Read + Write Fallback

Khi Edit thất bại (non-unique text), dùng Read để load toàn bộ file, sửa trong bộ nhớ, rồi Write:

# Step 1: Read the full file
content = Read(path="src/auth/tokens.ts")

# Step 2: Make the modification in the full content
# (you can target line numbers or use more context to make it specific)
updated = content.replace(
    "function validateToken", 
    "async function validateToken"
)  # Still only replaces once if first occurrence is correct

# Step 3: Write back
Write(path="src/auth/tokens.ts", content=updated)

4. Chiến lược hiểu Codebase theo kiểu tăng dần (Incremental)

Anti-pattern: Đọc tất cả file ngay từ đầu trước khi bắt đầu phân tích.

Correct approach: Xây dựng hiểu biết theo kiểu tăng dần, bắt đầu từ các entry point.

Chiến lược Incremental

Step 1: Glob — Find relevant files by pattern
Step 2: Grep — Find entry points, key functions, critical imports
Step 3: Read — Follow imports and trace code flows on demand
(Avoid reading files that haven't been referenced)

Example: Hiểu một Refund Flow

# Step 1: Find files related to refunds
refund_files = Glob(pattern="**/*refund*")
# → [src/services/refundService.ts, src/api/refundController.ts, tests/refund.test.ts]

# Step 2: Find all callers of processRefund
callers = Grep(pattern="processRefund", path="src/")
# → RefundController.ts:45, PaymentService.ts:120, OrderService.ts:89

# Step 3: Read only the relevant files
refund_service = Read(path="src/services/refundService.ts")
payment_service = Read(path="src/services/paymentService.ts")
# NOT reading all files in src/ — only what was referenced

Truy vết Exports qua các Wrapper Module

# Problem: function exported from wrapper module, not its origin file
# Solution: Find all exports first, then trace each

# Step 1: Find all exports from the index/barrel file
exports = Grep(pattern="export", path="src/utils/index.ts")
# → export { formatDate } from './dates'
# → export { sanitizeInput } from './security'
# → export { processPayment } from './payments'

# Step 2: Search for each exported name across the codebase
date_usages = Grep(pattern="formatDate", path="src/")
payment_usages = Grep(pattern="processPayment", path="src/")

5. Edit Failure Fallback Pattern

def safe_edit(path: str, old_str: str, new_str: str) -> bool:
    """
    Attempts Edit; falls back to Read+Write if old_str is not unique.
    Returns True on success.
    """
    try:
        Edit(path=path, old_str=old_str, new_str=new_str)
        return True
    except NonUniqueMatchError:
        # old_str appears in multiple places — use Read+Write with more context
        print(f"Edit failed: non-unique match in {path}. Falling back to Read+Write.")
        
        content = Read(path=path)
        
        # Count occurrences to understand the problem
        count = content.count(old_str)
        print(f"Found {count} occurrences of target text")
        
        if count == 0:
            print("Text not found in file")
            return False
        
        # Replace only first occurrence (if that's correct)
        updated = content.replace(old_str, new_str, 1)
        Write(path=path, content=updated)
        return True

def explore_unfamiliar_codebase(root_path: str, question: str) -> str:
    """
    Incremental codebase exploration strategy.
    Avoids reading all files upfront.
    """
    findings = []
    
    # Step 1: Understand project structure
    structure_files = Glob(pattern="**/*.{json,yaml,toml}", path=root_path)

    findings.append(f"Project type: {extract_project_type(package_json)}")

    entry_points = Grep(pattern="export default|module.exports|def main", path=root_path)
    findings.append(f"Entry points found: {len(entry_points)}")
    
    # Step 3: Based on the question, targeted search
    if "authentication" in question.lower():
        auth_files = Grep(pattern="authenticate|login|token|jwt|session", path=root_path)
        for file_match in auth_files[:5]:  # Top 5 most relevant

            findings.append(analyze_auth_pattern(content))
    
    elif "database" in question.lower():
        db_files = Glob(pattern="**/*{model,schema,migration}*")
        # Read only the most relevant models
        for f in db_files[:3]:
            findings.append(Read(path=f))

def find_callers_of_function(func_name: str, src_path: str) -> list:
    """Find all places a function is called — use Grep for content search."""
    return Grep(pattern=f"{func_name}\\(", path=src_path)


def find_and_update_import(
    old_import: str, 
    new_import: str, 
    src_path: str
) -> int:
    """Find all files importing from old_import and update them."""
    
    # Step 1: Find affected files using Grep (content search)
    affected = Grep(pattern=f"from '{old_import}'", path=src_path)
    
    updated_count = 0
    for match in affected:
        file_path = match.path
        
        # Step 2: Try Edit (targeted) on each file
        try:
            Edit(
                path=file_path,
                old_str=f"from '{old_import}'",
                new_str=f"from '{new_import}'"
            )
            updated_count += 1
        except NonUniqueMatchError:
            # Step 3: Fallback to Read+Write
            content = Read(path=file_path)
            updated = content.replace(
                f"from '{old_import}'",
                f"from '{new_import}'"
            )
            Write(path=file_path, content=updated)
            updated_count += 1
    
    return updated_count

    Generate tests while avoiding duplicates by reading existing test files first.
    Relevant for CI/CD scenario (Domain 3).
    """
    # Find existing test files
    test_files = Glob(pattern=f"**/*{func_name}*.test.*")
    
    existing_tests = []
    for test_file in test_files:
        existing_tests.append(Read(path=test_file))
    
    # Find the function implementation
    impl_matches = Grep(pattern=f"function {func_name}|def {func_name}", path=src_path)
    if impl_matches:
        impl = Read(path=impl_matches[0].path)
    
    # Generate tests (prompt with existing context to avoid duplicates)
    prompt = f"""
Generate test cases for {func_name}.
Implementation:
{impl}

Existing test cases (DO NOT duplicate these):
{chr(10).join(existing_tests)}

Generate only NEW test cases not covered above.
"""
    return prompt  # Send to Claude for test generation

1. The Three-Level CLAUDE.md Hierarchy

Claude Code tải các file CLAUDE.md từ nhiều cấp khác nhau, mỗi cấp có một phạm vi (scope) riêng:

Level 1: USER (~/.claude/CLAUDE.md)
  → Personal preferences, individual developer settings
  → NOT shared via version control
  → Applies to ALL projects for that user

Level 2: PROJECT (.claude/CLAUDE.md or root CLAUDE.md)
  → Team-wide standards and conventions
  → Committed to version control
  → Applies to everyone who clones the repo

Level 3: DIRECTORY (subdirectory CLAUDE.md)
  → Area-specific rules (e.g., src/api/CLAUDE.md)
  → Committed to version control
  → Applies only when working in that directory

Loading Order

Tất cả các file áp dụng được đều được tải và hợp nhất (các file cụ thể hơn có thể mở rộng hoặc ghi đè các file ở cấp cao hơn):

User CLAUDE.md
  +
Project CLAUDE.md
  +
Current directory CLAUDE.md (if exists)
  =
Effective configuration for current session

Critical Distinction: User vs Project Level

❌ WRONG: Instructions in ~/.claude/CLAUDE.md
  → Only applies to YOU
  → New team members won't receive these instructions
  → Instructions disappear when a different developer works on the project

✅ CORRECT: Instructions in .claude/CLAUDE.md (version controlled)
  → Applied to ALL developers who clone the repo
  → Consistent behavior across the team

Đây là lỗi cấu hình số 1 được kiểm tra trong kỳ thi.

  User: "Now help me fix the bug"

1. Why Path-Specific Rules?

Vấn đề: Một codebase có các convention khác nhau cho các khu vực khác nhau, và bạn muốn Claude tự động áp dụng đúng convention mà không phải:

  • Tải mọi thứ cùng lúc (lãng phí context, gây nhầm lẫn)
  • Yêu cầu gọi skill thủ công (dễ sai sót, không nhất quán)

Giải pháp: Các file .claude/rules/ với YAML frontmatter paths để kích hoạt rule chỉ khi đang chỉnh sửa file khớp.

The Key Advantage

Without path-specific rules:
  Developer edits Button.tsx → Claude applies React + API + DB + Terraform conventions
  → Confused, conflicting, irrelevant guidance
  → Wastes context window

With path-specific rules:
  Developer edits Button.tsx → Claude applies only React conventions (*.tsx match)
  Developer edits terraform/main.tf → Claude applies only Terraform conventions
  → Focused, relevant guidance
  → Efficient context usage

1. What is Plan Mode?

Plan mode cho phép Claude Code khám phá, phân tích và thiết kế trước khi thực hiện bất kỳ thay đổi nào. Model đọc file, lần theo luồng code, và tạo ra một kế hoạch — mà không write, edit hay chạy bất cứ thứ gì.

Đặc tính then chốt: An toàn để khám phá. Không có side effect trong giai đoạn lập kế hoạch.

When Plan Mode Activates

  • Người dùng chủ động vào plan mode: "use plan mode", "before making changes, plan this"
  • Đặc điểm của task báo hiệu là cần đến nó (phức tạp, mang tính kiến trúc, đa file)

Plan Mode Output

  • Phân tích trạng thái hiện tại
  • Đề xuất cách tiếp cận cùng các phương án thay thế đã được cân nhắc
  • Danh sách các file cần thay đổi và thay đổi như thế nào
  • Xác định rủi ro và các phụ thuộc (dependencies)
  • Chờ phê duyệt trước khi thực thi

2. Decision Framework

Use Plan Mode When:

Task involves ANY of:
  ✅ Changes to dozens or more files
  ✅ Architectural decisions (service boundaries, module structure)
  ✅ Multiple valid approaches that need evaluation
  ✅ Large-scale refactoring or migrations
  ✅ Library migrations affecting many files
  ✅ New features with infrastructure implications
  ✅ Unknown dependencies that need discovery first

Use Direct Execution When:

Task is ALL of:
  ✅ Clear scope (you know exactly what to change)
  ✅ Single file or small, well-defined set of files
  ✅ One obvious correct approach
  ✅ Simple bug fix with clear stack trace
  ✅ Adding a single validation, config value, or simple function
  ✅ Well-understood change with no architectural implications

The Core Principle

Plan mode = đầu tư thời gian ở giai đoạn đầu để tránh phải làm lại tốn kém

Plan mode cost:    Extra analysis time (minutes)
Plan mode benefit: Avoid discovering wrong approach after 2 hours of changes

Direct execution cost:    None (for simple tasks)
Direct execution risk:    Expensive rework if approach was wrong

3. The Explore Subagent

Explore subagent là một subagent chuyên dụng cho các giai đoạn khám phá dài dòng (verbose discovery) trong các task nhiều giai đoạn. Nó:

  • Đọc và phân tích file một cách tách biệt
  • Trả về một bản tóm tắt cô đọng cho context chính
  • Ngăn context của cuộc hội thoại chính bị lấp đầy bởi nội dung file

Why Explore Matters

Without Explore subagent:
  Main agent reads 50 files to understand codebase → context fills
  → Less room for actual implementation
  → Context degradation on long tasks

With Explore subagent:
  Explore subagent reads 50 files → returns 200-token summary
  → Main context stays clean
  → Full context available for implementation phase

Pattern: Plan with Explore, Then Execute

Phase 1: Explore subagent
  → Reads all relevant files
  → Maps dependencies
  → Returns: summary of current structure + migration checklist

Phase 2: Plan mode (using Explore's summary)
  → Uses compact summary to design migration approach
  → No need to re-read files

Phase 3: Direct execution (per planned steps)
  → Executes the approved plan step by step

4. Combining Plan + Direct Execution

Thực hành tốt nhất cho các task phức tạp: Lập kế hoạch cho cách tiếp cận, rồi chuyển sang direct execution theo kế hoạch đó.

"Plan the migration from lodash to native ES functions,
then execute the planned approach"

Step 1 (Plan mode):
  - Reads current lodash usage across 45 files
  - Groups by function: _.map → .map(), _.filter → .filter(), etc.
  - Identifies 3 complex cases needing manual review
  - Outputs: migration plan with file-by-file changes

[Developer reviews and approves plan]

Step 2 (Direct execution):
  - Executes planned changes file by file
  - Known approach, no surprises
  - No rework needed

## 2. Test-Driven Iteration

Viết test trước, rồi lặp lại bằng cách chia sẻ các test bị lỗi.

### The Pattern

Step 1: Write comprehensive test suite

  • Happy path tests
  • Edge cases (null, empty, boundary values)
  • Error condition tests
  • Performance requirements (if applicable)

Step 2: Share with Claude — "Make these tests pass"

Step 3: Review implementation, share failures "Tests 3, 7, and 12 are still failing: Test 3: Expected null for empty input, got empty string Test 7: Expected error for negative values, no error thrown Test 12: Performance test failing — 450ms average, requirement is < 200ms"

Step 4: Iterate with specific failures → targeted fixes


### Benefits Over "Fix the code"

- Test định nghĩa chân lý gốc (ground truth) — không mơ hồ về việc "đúng" nghĩa là gì
- Các test lỗi cung cấp thông báo lỗi cụ thể, có thể hành động được
- Ngăn regression (các test cũ vẫn tiếp tục pass)
- Test tồn tại như một dạng tài liệu

## 3. The Interview Pattern

Để Claude đặt câu hỏi làm rõ **trước khi** triển khai, nhằm làm lộ ra những điểm cân nhắc mà bạn có thể chưa lường trước.

### When to Use

Dùng interview pattern khi làm việc trong **các lĩnh vực chưa quen thuộc** hoặc khi bài toán có độ phức tạp ẩn:
- "Build a caching layer" → chiến lược cache invalidation là gì?
- "Add rate limiting" → theo từng user hay toàn cục? theo endpoint hay toàn cục?
- "Implement retry logic" → exponential backoff? jitter? số lần retry tối đa?

### How to Invoke

"Before implementing this, ask me 3-5 clarifying questions about requirements and constraints. Then I'll answer and you can implement."


### Example

User: Before implementing the session management system, ask me about requirements.

Claude:

  1. Should sessions expire after inactivity, fixed time, or both?
  2. Do sessions need to survive server restarts (persistent storage)?

1. The -p Flag for Non-Interactive Mode (Q10)

Đây là đáp án trực tiếp cho Q10.

# ❌ WRONG — hangs indefinitely in CI (waits for interactive input)
claude "Analyze this pull request for security issues"

# ✅ CORRECT — runs non-interactively, outputs to stdout, exits
claude -p "Analyze this pull request for security issues"
# OR equivalently:
claude --print "Analyze this pull request for security issues"

Why -p Fixes the Hanging Problem

Nếu không có -p, Claude Code vào chế độ interactive REPL và chờ input từ người dùng. CI pipeline không có người dùng tương tác → job bị treo vô thời hạn.

Với -p / --print:

  • Xử lý prompt
  • Xuất kết quả ra stdout
  • Thoát ngay lập tức mà không chờ input

What NOT to Do (Q10 Distractors)

# ❌ CLAUDE_HEADLESS=true — this environment variable does NOT exist
CLAUDE_HEADLESS=true claude "Analyze..."

# ❌ --batch — this flag does NOT exist in Claude Code
claude --batch "Analyze..."

# ❌ stdin redirect — workaround, not the correct solution
claude "Analyze..." < /dev/null

Multi-File Review: Avoid Attention Dilution (Q12)

Với các PR có 14+ file: tách thành các lượt review từng-file tập trung + một lượt integration.

def structured_pr_review(changed_files: list[str]) -> dict:
    """
    Q12 correct approach: per-file passes + cross-file integration pass.
    """
    # Phase 1: Focused per-file local analysis
    file_reviews = []
    for file_path in changed_files:
        review = subprocess.run(
            ["claude", "-p",
             f"Review only {file_path} for local issues: bugs, null handling, error cases.",
             "--output-format", "json"],
            capture_output=True
        ).stdout
        file_reviews.append(json.loads(review))
    
    # Phase 2: Cross-file integration analysis
    integration_review = subprocess.run(
        ["claude", "-p",
         "Review these files for cross-file issues: data flow, API contracts, "
         "shared state inconsistencies, circular dependencies.",
         "--files", " ".join(changed_files),
         "--output-format", "json"],
        capture_output=True
    ).stdout
    
    return {
        "file_reviews": file_reviews,
        "integration_review": json.loads(integration_review)
    }

Tại sao KHÔNG chọn Option C (context window lớn hơn): Context window lớn hơn không khắc phục được chất lượng attention — model vẫn xử lý tất cả file cùng lúc, dẫn đến độ sâu không đồng đều.

Tại sao KHÔNG chọn Option D (majority vote): Yêu cầu 2/3 lần chạy đồng thuận sẽ TRIỆT TIÊU những bug chỉ bị bắt được không thường xuyên. Một bug xuất hiện ở 1 trong 3 lần chạy vẫn là một bug thực sự.

1. The Problem with Vague Instructions

Mơ hồ: "Check that comments are accurate" Kết quả: Gắn cờ những comment thiếu chính xác, mang tính chủ quan, hoặc khác biệt về phong cách — false positives

Tường minh: "Flag comments ONLY when the claimed behavior contradicts the actual code behavior" Kết quả: Chỉ gắn cờ những comment sai một cách khách quan — ít false positives hơn

Vì sao hướng dẫn mơ hồ gây ra FP

Model diễn giải "accurate" theo nghĩa rộng:

  • Một comment nói "sanitizes input" nhưng thực tế lại truncate nó → true positive (behavior mismatch)
  • Một comment nói "returns user" nhưng lại trả về một DTO → bị model gắn cờ (khác biệt ngữ nghĩa nhỏ)
  • Một comment đã lỗi thời nhưng về mặt kỹ thuật vẫn đúng → đôi khi bị gắn cờ

Với tiêu chí tường minh, model có một phép kiểm nhị phân rõ ràng: code có làm đúng những gì comment nói không?

2. Explicit Criteria vs Confidence Filtering

Điểm phân biệt quan trọng trong kỳ thi:

ApproachExampleEffectiveness
Explicit categorical criteria"Report bugs and security issues; skip style issues"✅ High
Confidence filtering"Only report high-confidence findings"❌ Low
Vague instructions"Be conservative"❌ Low

Vì sao lọc theo độ tin cậy thất bại

Độ tin cậy do model tự báo cáo không tương quan tốt với mức độ đúng thực tế:

  • Tự tin cao vào những thứ nó sai (đã tự tin trên các ca khó theo Q3)
  • Tự đánh giá mang tính vòng lặp — cùng một chuỗi lập luận tạo ra finding cũng chính là chuỗi đánh giá độ tin cậy

Từ đề thi Q3: "The agent is already incorrectly confident on hard cases" — thêm ngưỡng độ tin cậy không giúp ích vì hiệu chuẩn độ tin cậy của model bị lỗi.

3. Defining Severity with Code Examples

Đưa vào các ví dụ code cụ thể cho từng mức độ nghiêm trọng để đạt được sự phân loại nhất quán:

## Severity Definitions

### HIGH — Must Fix Before Merge
Issues that cause incorrect behavior, data loss, or security vulnerabilities.

Example HIGH issues:
```python
# HIGH: SQL injection — user input directly in query
query = f"SELECT * FROM users WHERE email = '{user_input}'"

# HIGH: None not handled — will raise AttributeError
def get_user_name(user):
    return user.name  # crashes if user is None

# HIGH: Credentials in code
API_KEY = "sk-real-key-here"

MEDIUM — Should Fix

Issues that degrade reliability or maintainability but don't cause immediate failures.

Example MEDIUM issues:

# MEDIUM: Error swallowed silently
try:
    process_payment()
except Exception:
    pass  # Error hidden — will cause confusing behavior later

# MEDIUM: Wrong HTTP status code
return Response({"error": "Not found"}, status=200)  # Should be 404

LOW — Consider Fixing

Stylistic or minor issues that don't affect behavior.

Example LOW issues:

# LOW: Variable name could be clearer
x = get_user()  # 'x' is non-descriptive

# LOW: Inline comment could be a docstring
def calculate_total(items):
    # multiplies price by quantity for each item
    return sum(item.price * item.quantity for item in items)

SKIP — Do Not Report

  • Local team patterns that differ from general conventions
  • Style issues handled by automated linters
  • Trivial formatting differences

extraction_tool = {
    "name": "extract_invoice_data",
    "description": "Extract structured data from an invoice document",
    "input_schema": {
        "type": "object",
        "properties": {
            # Required fields — always present
            "invoice_number": {"type": "string"},
            "vendor_name": {"type": "string"},
            
            # Optional (nullable) — may not exist in document
            "purchase_order": {
                "type": ["string", "null"],  # nullable
                "description": "PO number if referenced in invoice"
            },

            "payment_method": {

            },
            "payment_method_detail": {
                "type": ["string", "null"],
                "description": "Required when payment_method is 'other'"

def validate_extraction(data: dict) -> list[str]:

Một model đã sinh ra code sẽ giữ lại ngữ cảnh lập luận của nó. Nó ít có khả năng đặt câu hỏi về chính các quyết định của mình.

  • Cùng một chuỗi lập luận tạo ra bug cũng chính là chuỗi "validate" code
  • Neo nhận thức (cognitive anchoring): "I wrote this, so it must be correct"
  • Phiên generator có xu hướng thiên vị việc xác nhận lựa chọn của chính nó

2. Kiến trúc Multi-Pass (đáp án Q12)

PR with 14 files → SPLIT into:

Pass 1: Per-file local analysis
  - Each file reviewed independently
  - Catches: null handling, logic errors, missing error handling
  - Full attention on one file at a time

Pass 2: Cross-file integration analysis
  - Cross-cutting concerns only
  - Catches: data flow issues, API contract mismatches, circular deps
  - Focused on inter-file relationships

NOT: All 14 files in one pass

Vì sao KHÔNG chọn các phương án thay thế này (Q12)

  • Option C (larger context window): Context lớn hơn ≠ chất lượng attention tốt hơn. Vẫn xử lý 14 file, vẫn gây pha loãng attention.
  • Option D (3-run consensus): Một bug được phát hiện ở 1/3 lần chạy vẫn là bug thật. Yêu cầu đồng thuận 2/3 sẽ ĐÈ NÉN các finding không liên tục.

                  f"{len(state['pending'])} remaining")

        all_files = glob(f"{path}/**/*.py", recursive=True)

from dataclasses import dataclass
from enum import Enum

class ReviewDecision(Enum):
    AUTONOMOUS = "autonomous"
    RECOMMEND_REVIEW = "recommend_review"  
    REQUIRE_REVIEW = "require_review"

@dataclass
class ReviewRoutingConfig:
    high_value_threshold: float = 10000
    new_vendor_auto_approve_limit: float = 500
    missing_fields_threshold: int = 2

def route_for_review(extraction: dict, config: ReviewRoutingConfig) -> ReviewDecision:
    """
    Route based on EXPLICIT CRITERIA, not confidence scores.
    """
    # High-value → require review
    if extraction.get("amount", 0) > config.high_value_threshold:
        return ReviewDecision.REQUIRE_REVIEW
    
    # Too many missing fields → require review
    missing = sum(1 for f in ["vendor", "date", "amount", "invoice_number"]
                  if not extraction.get(f))
    if missing >= config.missing_fields_threshold:
        return ReviewDecision.REQUIRE_REVIEW
    
    # New vendor below threshold → recommend
    if extraction.get("is_new_vendor") and \
       extraction.get("amount", 0) <= config.new_vendor_auto_approve_limit:
        return ReviewDecision.RECOMMEND_REVIEW
    
    return ReviewDecision.AUTONOMOUS
